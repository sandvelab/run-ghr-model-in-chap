alternatives-considered: assembling the answer from the runs already lying around in the tree
  and in git history, without re-running anything. That was built first and rejected: it is
  cheap and it answers a different question. "Does it run again from clean" is answered by
  running it again from clean, and a route that had quietly stopped working would still have
  looked fine in a table of old metrics files.
  Collapsing identical results was also rejected, and this was a real defect in the first
  version: deduplicating by file content reported route B as having run **once**, because its
  numbers are byte-identical every time. That is the opposite of what repeatability means —
  identical numbers are the strongest evidence a route re-ran, not evidence it did not. Runs
  and distinct results are now counted separately, and `bit_reproducible` is reported in its
  own column.
  Each repeat writes into this node rather than into the route's, so a repeat never overwrites
  the run the reports quote.
  The spread is reported and not corrected for (plan §2, §3): a route whose numbers move a few
  per cent between identical invocations is a working route, and exact reproducibility is not
  a condition of success here.
