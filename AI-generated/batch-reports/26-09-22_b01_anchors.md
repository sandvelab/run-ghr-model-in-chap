# Batch 1 — the anchors, pinned and verified

Generated from [[26-09-21_chapModelIntegrationRoutes]] — iteration 2

Phase A. The three anchors this project is bound to are fixed and checked against the files
on disk; the Lao dataset is characterised from the CSV and its CHAP schema; the analysis tree

## What was pinned

| Anchor | Pinned at | Where |
|---|---|---|
| Platform | `chap-core` **2.3.1**, resolving `chapkit` **2.1.0** and `servicekit` **2.0.2** | `Archive/platform-chap/` |
| Route A model | `chap-models/chapkit_ghr_model` @ `60b16a2`, GPL-3.0 | `Archive/model-route-a/` |
| Route B model | `dhis2-chap/minimalist_example_uv` @ `5cd8a12`, no licence declared | `Archive/model-route-b/` |
| Data | `dhis2/climate-health-data`, `lao/` @ `af362d5`, no licence declared | `Archive/data-lao/` |

The platform was captured from the live installation — `chap --version`, the entry point, the
`uv` tool listing and receipt, and a 176-package freeze of the interpreter behind `chap`.

**Three versions are recorded where one would be the obvious choice.** A chapkit model
service negotiates with `chapkit`, and `chap-core`'s version does not determine which
`chapkit` is behind it: across released versions that requirement has been unbounded above in
one and capped below 2 in others. A pin naming only `chap-core` would therefore be ambiguous
in exactly the place the two routes differ from each other, so `chapkit` and `servicekit` are
pinned in their own right and the reason is written into the anchor's `provenance.md`.

The two model anchors and the data anchor were not re-fetched. They stand at the commits they
were archived at, verified in place — the plan's §4b records why: the platform is meant to be
the only anchor that moves, and a re-fetch would risk an upstream change confounding a
difference in route cost with a difference in the model or the data.

## What was verified, and how

`analysis/01_anchors/scripts/verify_anchors.py`, run through `analysis/01_anchors/run.sh`
under the pinned analysis environment. It reads nothing from the plan. Eight checks, all
passing (`results/anchor_manifest.tsv`):

- each of the three Lao files re-hashed against the digest in `sha256sums.txt`, written when
  they were fetched — all three match;
- each model clone present, with the commit read out of its own `git-metadata.txt`;
- `chap --version` compared against the `chap-core` line of the platform's freeze — they
  agree — and the resolved `chapkit` and `servicekit` read out of the same freeze.

The node makes no network call, so it runs offline and re-runs identically. The cost is that
it does not check whether the two pinned commits still exist upstream; that is recorded in
the provenance record as an alternative considered.

## What the data turned out to be

*(`analysis/01_anchors/results/lao_characterisation.tsv` — 24 properties, each with the file
it was read from)*

An **18-unit, 156-month admin-1 panel for Laos, 1998-01 to 2010-12, 2808 rows**, keyed on
`location` + `time_period`. The target is `disease_cases`, reported dengue cases from
OpenDengue. Beside it: `population`, `rainfall`, `mean_temperature` and
`mean_relative_humidity`, none with a missing value. **233 rows have no target value.**

The covariate list is a reading of the CSV header, not a statement about what either model
will be given. Establishing how CHAP wants a dataset presented is part of what each route's
agent has to discover, and the orchestrator settling it first is the contamination the plan's
§3 forbids — so this node deliberately stops at the files.

## Three inconsistencies, recorded and kept

*(`analysis/01_anchors/results/anchor_discrepancies.tsv`)*

| Where | Declared | Actually |
|---|---|---|
| `schema.dataset.row_count` | 2575 | 2808 rows in the file; 2575 is the count of rows that *have* a target |
| `schema.dataset.admin_geojson_file` | `LAO_ADM1.geojson` | the file shipped beside the CSV is `chap_LAO_admin1_monthly.geojson` |
| `disease_cases` | complete | 233 values absent; `LA-VI` has none at any period, leaving 17 of 18 units with a target |

**None is repaired.** This is the substantive judgment call of the batch, and it is
`agent-autonomous`: how each route copes with a schema that disagrees with its own data, a
boundary file under a different name, and a gappy target is part of what the project
measures. Repairing them would remove the thing being observed and would change the panel the
two routes are compared on.
